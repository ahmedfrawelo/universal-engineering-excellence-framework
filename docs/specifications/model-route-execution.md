# Dynamic Codex Model Routing Specification

## Objective

Make UEEF discover the signed-in Codex account's actual model catalog, select a concrete model and reasoning target for each work unit, and record the result. The selected route must be consumable by a host integration and auditable from a command result.

## Requirements

1. One versioned policy owns T0-T4 capability classes, the per-work-unit invocation cycle: T0-T3 use `low`, `medium`, `high`, then repeat; T4 uses `medium`, `high`, then repeat. It also owns the hard default ceiling of `high`, explicit override rules, and capacity-fallback limits. It owns no model catalog and no repository-authored effort display-name mapping.
2. `scripts/codex-app-server-models.mjs` calls the signed-in Codex App Server `model/list` at dispatch time, including every returned page and hidden entry. On Windows it resolves the executable from an explicit override, then the active `CODEX_HOME` runtime, then `PATH`; this avoids treating an inaccessible WindowsApps alias as account unavailability. No screenshot-derived, hand-maintained, cached, or caller-supplied account catalog is allowed in production.
3. Each tier chooses a capability class. For the same stable work-unit ID, the managed session records an invocation counter only after a matching successful execution: T0-T3 select `low`, then `medium`, then `high`, then repeat; T4 selects `medium`, then `high`, then repeats and fails closed when either required effort is unavailable. Unsupported standard labels outside the strict T4 contract fall back to that model's own ordered host efforts. Every catalog entry receives a coverage record containing its exact identifier, host efforts, inferred capability class, visibility, upgrade metadata, and routing eligibility. Picker-visible general models in the best capability class form the work-unit distribution pool; a stable hash of the tier and work-unit ID selects within that pool and the next member is the one capacity fallback. Thus every eligible model is used across work units without random drift, hardcoded names, or persistent learning state. Host-hidden specialized models remain covered but require a matching specialist purpose and are never sent to unrelated general work. The router reports the exact technical identifier supplied by the host and uses a host-supplied effort display name only when that catalog entry supplies one. It never translates or invents effort names. The number of supported efforts is never used as a proxy for model capability.
4. PowerShell and Unix route selectors consume the same dynamic catalog and emit the same route fields.
5. The current conversation's picker selection is used only with the explicit `--use-current-model --current-model <id>` request. Otherwise a model-routed work unit is selected independently.
6. A capacity failure is recorded as external provider capacity, never hidden or solved by rotating accounts. One fallback is allowed.
7. An actual host execution must record the model and effort actually used. UEEF must not claim that it changed the model picker of an already-running Codex conversation unless `scripts/update-codex-thread-settings.mjs` updated a caller-supplied target `threadId` and observed a matching `thread/settings/updated` event.
8. Re-run routing for every materially different work unit and whenever scope, ambiguity, risk, or verification needs change. Before dispatch, show the selected model and the host-provided effort name. If the next route differs, show the changed route before executing it.
9. A Tier is a difficulty/capability class, not a single-model alias. For a stable work-unit ID, distribute deterministically across every general catalog model in the best matching host-derived capability class. This makes all eligible models executable without random drift or repository-authored model names. Hidden models remain excluded from general work and become eligible only when an explicit specialist purpose matches their host description.
10. Every T0-T4 work unit must complete a matching model dispatch before other task tools run. After dispatch, show `Model execution: <work-unit> | <actualModel> / <actualEffort> (verified: <source>)`; a route request alone is not proof. Any routed sub-agent preserves the user's language by default and may receive a BCP-47 response-language tag such as `ar`. The repository graph viewer must surface recent routing receipts from `.ueef/evidence` so the user can distinguish verified execution from the visible picker state.

## Execution Contract

For a routed task, `scripts/resolve-model-route.mjs` actively calls `scripts/codex-app-server-models.mjs`; it never silently uses a saved catalog. A `--catalog` path is accepted only as an explicit `test-fixture` simulation and can never become account-verified. If App Server does not return a catalog, the route stays unresolved and the task remains active.

The App Server envelope is produced at dispatch time with `provenance.provider = codex-app-server:model/list`, the current discovery timestamp, every returned model page (including hidden entries), and each model's own ordered `supportedReasoningEfforts`. It is transient task evidence, not a repository catalog or a cross-session cache. Adding or removing a model in the account therefore changes the next route without a source edit. This includes separately offered models such as `gpt-5.3-codex-spark` when the signed-in account exposes them.

Account verification is direct and fail-closed: only the resolver's own App Server `model/list` response can qualify, and it must have a current discovery timestamp, unique model IDs, and a non-empty unique effort list for every model. The managed `record-ueef-route.mjs` invokes the same resolver, stores a digest-bound work-unit route, increments its revision on re-route, exposes the exact route line, and reports catalog coverage counts. A plain four-field prose record or external JSON file is insufficient.

- `ROUTED_LEAD_REQUIRED`: publish `Model route: <work-unit> | <preferredModel> / <displayReasoning> (host: <hostReasoning>)`, then start the work unit with the exact `preferredModel` and `hostReasoning` values. `preferredModel` is always the complete technical model identifier returned by Codex, never a shortened display nickname. This disclosure is mandatory for every UEEF task. Do not infer or hallucinate a model from the picker, a screenshot, a subagent's prose, or assistant self-identification; if the actual pair is not proven by host evidence, publish `Model used: UNVERIFIED` and keep completion unproven. On a later change publish `Model route changed: <work-unit> | <old> -> <new>` before dispatch. The managed hook reads the assistant-message stream and denies the next local tool until that exact current route line is user-visible; a recorder command's own output does not satisfy the visibility gate. The original conversation remains responsible for scope, evidence, integration, and closure.
- An explicit request to use the current picker adds `--use-current-model --current-model <id>`. If that model cannot satisfy the route, remain unresolved. Only an explicit user permission to break the constraint adds `--allow-model-constraint-override`. An effort above `high` similarly requires the explicit `--allow-exceed` flag.
- `record-ueef-route.mjs --route-output <live-route.json>` writes the complete digest-bound route consumed by `scripts/codex-app-server-dispatch.mjs`. A canonical catalog fingerprint covers ordered model identifiers, visibility, capability, efforts, defaults, and upgrade metadata; the route digest includes that fingerprint plus both primary and fallback pairs. The dispatcher uses the signed-in App Server with an ephemeral thread, disables provider fallback, records the effective full model identifier from `thread/start` and every `model/rerouted` notification, and proves the executed turn effort from `thread/settings/updated` rather than the thread default. It never treats the child model's prose self-report as execution evidence. The managed hook accepts only a structured App Server receipt with matching provider, thread/turn IDs, full verification source, disabled provider fallback, route digest, exact pair, and `SUCCESS`. Then call `scripts/record-model-route-result.mjs --route <live-route.json> --dispatch-result <app-server-result.json> --output <receipt.json>`. Legacy host dispatches still require a matching `read_thread` completion observation. The recorder refuses fixtures, stale/unverified catalogs, missing or recomputed-digest mismatches, unverifiable results, and pairs outside the primary route or its one fallback. A capacity rejection requires the exact signal plus a host request/turn ID; fallback `SUCCESS` accepts the dispatcher's bound aggregate attempts or a separate hash-bound primary `CAPACITY` receipt.
- On `Selected model is at capacity`, attempt only the declared fallback once. Record the primary failure and fallback actually used. Do not rotate accounts, profiles, cookies, or secrets. If no fallback can run, retain the task as active and report the external capacity condition.

Model selection is a host operation. The selector does not automatically mutate the model dropdown of an already-running primary conversation, but it does select the model that performs a routed work unit. When a visible picker change is explicitly requested, `scripts/update-codex-thread-settings.mjs` may call App Server `thread/resume` followed by `thread/settings/update` only for an exact caller-supplied `threadId`; it must not infer the current UI thread from a route, receipt, browser tab, profile, or local evidence file. The managed hook denies all T0-T4 task tooling until the current visible route has a matching dispatch. It then denies continuation until the verified actual full model and effort line is user-visible. Recording a new work-unit route resets that dispatch evidence.

## Acceptance Evidence

- `scripts/test-model-routing-policy.mjs` proves catalog consumption, full-catalog coverage, hidden-specialist handling, T0-T3 low/medium/high cycling, T4 medium/high cycling, account additions/removals, host-supplied display names, the high ceiling, explicit-current-model behavior, explicit overrides, and unavailable-catalog behavior.
- `scripts/test-managed-enforcement.ps1` proves that recording a route is insufficient until the exact full model identifier and effort line appears in an assistant message, and that a changed route must be shown again before dispatch.
- `scripts/test-agent-route.ps1` and `.sh` prove both selectors surface the same dynamic route fields.
- `scripts/test-codex-thread-settings-update.mjs` proves picker mutation requires an explicit thread ID and a matching App Server settings update notification.
- `scripts/test-repository-intelligence-viewer.mjs` proves the offline graph viewer can render its routing evidence panel without breaking graph search and navigation.
- A live App Server run records the actual account catalog and the actual model/effort used. Fixture tests do not substitute for this evidence.
